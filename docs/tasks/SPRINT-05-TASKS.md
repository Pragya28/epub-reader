**Bug caught via live verification, not by the test suite (2026-08-06):** `useReaderChrome()` returns a fresh object every render; `use-reader-screen.ts` originally kept that whole object as `const chrome = useReaderChrome()` and depended on it (`[chrome]`) in `handleExternalLink`'s `useCallback`. That gave the callback a new identity every render, which — since it's passed as `onExternalLink` into `useReaderEngine`'s dependency array — re-ran that whole effect on every render, repeatedly calling `initializeChapterDocument` and wiping the just-mounted iframe. The bug was invisible in the unit test suite (which mocks `useReaderEngine` entirely) and even invisible in a quick screenshot — it only surfaces as "chapters never actually render, despite the store saying they loaded" when you inspect the live iframe's DOM after a real EPUB import. Caught by importing a real fixture book through the app's actual `importBook()` pipeline (fetched via Vite's `/@fs/` dev-server path, no file-upload capability needed) and checking `iframe.contentDocument.body.children.length` directly — not something a screenshot alone would have shown. Fixed by destructuring `useReaderChrome()`'s return at the call site (`const { visible: chromeVisible, handleScrollDirection, toggle: toggleChrome, setOverlay: setChromeOverlay } = useReaderChrome();`) instead of keeping one object reference, so every consumer holds the individual stable function references directly. A second, smaller bug from the same live pass: the reader-toolbar sheet's `h-[40dvh]` override was silently losing to `sheet.tsx`'s base `data-[side=bottom]:h-auto` — a data-attribute variant selector beats a plain class selector on CSS specificity regardless of source order, so the override needed the matching `data-[side=bottom]:` prefix to actually win. **Two real bugs found via live/user report, not the test suite (2026-08-07):**

1. **`.folio-header` hardcoded `position: sticky`** (`src/index.css`) — it lives in the same `@layer utilities` as Tailwind's own utility classes, so on any element also carrying Tailwind's `absolute` (same specificity, `.folio-header` defined later in the cascade), `sticky` silently won. This was invisible-looking in isolation but broke the _reader's_ footer (Day 3, `position: absolute; bottom-0`): its computed position was actually `sticky`, so it had no viewport-bottom anchor and rendered in normal document flow immediately below the header instead — the "header and footer render together" report. Confirmed via `getComputedStyle(footer).position === "sticky"` before the fix, `"absolute"` after. Fixed by removing the hardcoded `position` from `.folio-header` entirely — every caller already sets its own (`sticky` on library-author/settings headers, was-meant-to-be-`absolute` on the reader's header/footer, now also the library header below).
2. **Library header flicker on scroll** — root-caused with a `MutationObserver` replay rather than guessed at: the scroll-direction detector in `use-library-screen.ts` had zero tolerance, so any 1px `scrollY` change (routine during momentum/rubber-band deceleration) flipped the header visible/hidden. Measured **14 toggles in 20 seconds** from one scroll gesture before the fix, **2 clean transitions** after adding an 8px minimum-delta threshold before honoring a direction change. This is also what motivated dropping the grid-rows approach in #21 above — an in-flow element whose height is scroll-driven visibly squeezes its children (logo, icon buttons) mid-transition independent of the flicker bug, so `fixed` positioning was strictly better on both counts.

Also fixed as part of the same pass: `continue-reading-banner.tsx`'s progress bar had a `flex-col items-center` wrapper, which collapses a `flex-1` child's width to zero on the cross axis — the progress fill was invisible regardless of color (a layout bug initially misdiagnosed as a color-contrast bug). And `reader-iframe-styles.ts`'s body `padding: 0 var(--reading-margin)` was changed to `padding: 120px var(--reading-margin)` — without vertical padding, the first/last lines of a chapter sit at the very edge of the scroll container and get hidden behind the reader's `absolute` header/footer chrome.
